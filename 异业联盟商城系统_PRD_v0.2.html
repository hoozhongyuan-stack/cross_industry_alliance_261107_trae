01

结论先行

本期把“异业联盟”收敛为本地多商户聚合商城：同一区域、不同行业的门店进入同一个入口，共用一套交易、履约与结算能力。跨店会员、积分、联盟套餐与分销分润不在本期，避免首版被权益互通拖垮。

D1

单店单订单，不做跨店购物车

一次下单只对应一个商户，支付、退款、售后、结算都以订单为单位。跨店合并支付会把拆账、拆单与售后责任放大数倍，放到 P1。

D2

平台收款，虚拟账户记账

用户通过微信支付付款进入平台收款账户；系统按订单把商户应得收入记入其虚拟收入账户；商户发起提现后由平台财务线下打款并回填凭证。平台只做记账，不调起自动分账。该模式存在资金归集与二清合规风险，上线前必须由财务/法务确认 Q1。

D3

商户即门店，1:1 绑定

一个商户账号对应一个门店、一套商品、一个虚拟收入账户与一个提现银行卡。连锁多门店、总部-分店模型放到 P1，首版不引入层级。

D4

一笔订单一种履约方式

实物配送、到店自提、到店服务（核销/预约）三选一；购物车内混选时在结算页拦截并引导分开下单。保证订单状态机与履约动作单一、可追踪。

D5

商品只分两类：实物与服务

实物有库存、配送/自提；服务有核销有效期、可预约时段与退款规则。服务是本地联盟的主力品类，必须和实物分开建模。

D6

联盟玩法后置到 P1

会员共享、积分互通、跨店联盟券、异业推荐分润本期不做；本期“联盟”体现在同一入口、同一账户、统一服务标准。先跑通交易与结算闭环，再叠加权益。

P0 一句话验收 用户能在本地完成「找店 → 下单 → 到店使用 / 收货」；商户能在商户中心完成「入驻 → 上架 → 接单 → 履约 → 对账提现」；平台能完成「审核 → 仲裁 → 规则 → 结算」的闭环，且每笔已支付订单都能追溯到支付、履约、售后与结算记录。

02

背景与目标

本地商户的线上化困难不在“有没有商城”，而在获客、履约、对账三件事彼此割裂。单店自建小程序没有流量，依赖团购平台则用户与交易数据都不属于自己；同时，跨行业商户各自为战，用户在同一个商圈内缺少统一入口。

问题 01

单店获客成本高，用户不属于门店

团购平台抽佣高、活动规则由平台制定，商户难以沉淀自己的复购用户。

问题 02

交易与履约分散

预约、核销、发货、售后各用一套工具，订单状态无法统一追踪，纠纷时缺少证据链。

问题 03

多商户资金结算复杂

平台收款后需要按佣金、退款、售后责任拆分给不同商户，人工对账不可持续。

产品回应与可观察结果

观察到的矛盾产品决策可观察的结果
单店缺少本地流量入口一个本地入口聚合多行业门店，按位置就近展示用户可在附近列表中进入任意行业门店并完成下单（FR-U-02 / 03 / 04）
履约动作因行业而异统一订单主状态 + 三种履约子流程商户在同一工作台完成接单、发货/备货、核销（FR-M-04 / 05）
多商户收入记账与退款无据可查平台收款 + 虚拟账户记账，按订单生成结算单每笔订单的收入、佣金、退款、结算均有明细与状态（FR-A-06 / SR-02）
平台治理缺少抓手入驻审核、商品审核、仲裁、规则版本化审核、仲裁、规则变更均留痕，敏感操作需二次确认（FR-A-02 / 04 / 05）

目标（以可观察行为描述，不设虚构指标）

  • 消费者：完成一次微信授权后，能够从附近门店进入商品、完成支付，并凭核销码或物流信息完成履约。
  • 商户：从提交入驻到完成首单履约，全部动作在商户中心内闭环，不依赖线下人工登记。
  • 平台：每一笔已支付订单都能追溯到支付单、履约记录、售后记录与结算单；每个敏感操作都有操作人、时间与原因。
  • 治理：违规商户可被停业/封禁，在途订单有明确处理规则，不会因封禁产生资金与履约真空。

3.2 P1 与本期不做

P1 · 交易与权益

联盟化能力

跨店购物车与合并支付、跨店会员卡与积分互通、联盟套餐/跨店券、异业推荐分润、拼团/秒杀/直播、优惠券与满减、平台补贴。

P1 · 经营与治理

规模化能力

连锁商户多门店、总部-分店模型、第三方同城运力调度、发票、电子合同、商户保证金、信用与风控模型、开放 API、骑手端。

边界说明 本期不做“跨店购物车”不是能力缺失，而是刻意约束：一旦允许跨店合并支付，支付单需要拆分为多个商户子单，退款、售后、结算与仲裁责任都会成倍复杂。首版以“单店单订单”换取可交付与可对账。

3.3 约束性要求

类型要求影响

位置与隐私位置授权需明确用途与关闭方式；拒绝定位不影响手动选区浏览；用户手机号、地址在平台后台脱敏展示。FR-U-02 / FR-U-13 / FR-A-08

04

角色与产品模型

三端共 7 个后台角色 + 1 个消费者角色。角色差异不只是“能看到什么”，更关键的是“能对钱和状态做什么”。

4.1 角色与数据边界

端角色核心职责数据边界
消费者端普通用户浏览、下单、支付、核销/收货、售后、评价仅本人订单、地址、售后记录
商户中心店长门店信息、商品、订单履约、核销、售后、结算提现、店员管理仅本门店全部数据与资金
店员接单、核销、查看订单、查看售后本门店订单；不可见金额明细、结算与提现
平台后台超级管理员账号与角色、规则发布、全部业务、系统配置全平台
运营商户/商品审核、内容位、用户管理、经营看板全平台业务数据；不可打款、不可改规则
审核员商户与商品审核、资质核验审核资料；不可见资金操作
客服 / 仲裁订单查询、售后仲裁、纠纷举证、工单跟进订单与举证资料；退款需财务复核
财务结算单复核、提现审核、线下打款、记账、退款复核、对账全平台资金数据；不可修改商品与订单

系统角色：超时关单、自动确认收货、账单生成等由系统执行，操作日志中记录为“系统”，并保留触发规则编号。

4.3 术语

术语定义
履约商户完成订单承诺的动作：发货、备货待提、确认预约、到店核销。
核销服务订单到店后，由商户扫码或输入核销码，将订单标记为已使用。核销不可由用户自行操作。
预约服务类订单在下单时选择到店时段，商户确认后生效；未预约的服务订单在有效期内可直接到店核销。
虚拟收入账户平台为每个商户建立的账面账户，记录订单收入、佣金、退款冲回、提现与调整；余额仅代表平台应付，不是实际银行资金。
结算平台按结算周期 N 天汇总商户可结算订单，生成结算单并转入商户虚拟收入账户的可提现余额。
提现商户从虚拟收入账户发起余额转出，平台财务审核后线下银行转账，并回填打款凭证完成记账。
可结算金额订单商品实付扣除佣金、退款与商户承担补偿后的金额，不含冻结中的售后订单。
冻结售后中或存在争议的订单金额暂不计入可提现，待结论后释放或扣减。
仲裁商户与用户对售后结论不一致时，由平台客服依据举证材料作出最终判定。
爽约预约订单在约定时段未到店核销，且用户未在允许时限内取消。
05

核心流程与界面

三条旅程共用同一套订单与资金模型：用户产生订单，商户履约，平台治理并结算。界面示意用于确认结构与状态入口，不是最终视觉稿。

5.1 用户旅程

进入并授权→ 定位 / 选区域→ 附近门店→ 商品详情→ 结算支付→ 到店核销 / 收货→ 评价 / 售后

关键分叉：用户拒绝定位时走手动选区；商品为服务时结算页多一步预约时段；支付后进入待接单，商户拒单或超时未接单则自动原路退款。售后入口只对允许售后的状态开放。

5.2 商户旅程

提交入驻→ 平台审核→ 门店设置→ 发布商品→ 商品审核→ 接单履约→ 售后处理→ 对账提现

审核驳回可修改重提，历史版本保留；商品被下架不影响已支付订单履约；售后拒绝后用户可申请仲裁，商户需在时限内举证。

5.3 平台旅程与资金流

商户/商品审核→ 规则配置→ 订单监控→ 售后仲裁→ 账单生成→ 提现审核与线下打款

示意图表达资金方向与记账责任。结算周期 N 天、起提金额、提现手续费与线下打款时效由 Q2 决策后落入配置。

FR-U-06 下单与支付：关键规则

结算页要素

用户必须看清什么

门店与履约方式、商品行与数量、配送费、实付金额、联系人/地址或预约时段、退款规则摘要、预计履约时间。服务类必须同时展示核销有效期与预约取消规则。

金额快照

支付金额以快照为准

提交订单时生成商品价格、配送费与佣金规则快照；商户改价不影响已生成订单；结算页刷新时若价格或库存变化，必须提示用户重新确认后再支付。

幂等

不产生重复订单与重复扣款

同一用户对同一购物内容重复提交需返回同一待支付订单；支付回调按支付单号幂等处理；重复支付的额外款项自动识别并退款 TBD。

顺序校验项失败时的产品行为
1登录状态未登录时唤起授权或登录，登录成功后回到结算页并保留已选商品与时段。
2门店状态休息中、停业、封禁时禁止下单，提示原因并推荐同区域同类门店。
3商品状态下架、售罄、超出配送范围时拦截该商品，提供移除或替换入口，不整单静默失败。
4履约能力预约时段已满、配送地址超出范围时置灰对应选项，并给出最近可用时段/范围。
5价格与库存变价或库存不足时展示最新价格与剩余数量，要求用户重新确认后才可支付。
6支付结果支付失败保留待支付订单 15 分钟；支付中断可回到订单详情继续支付；超时关闭并释放库存。

库存与预约时段在下单时预占，支付超时、取消、商户拒单时释放；并发下以服务端扣减结果为准，不允许超卖。

FR-A-04 售后仲裁：受理与判定

流程

五步闭环

1 用户申请售后 → 2 商户处理或超时 → 3 用户申请仲裁 → 4 平台受理并要求双方举证 → 5 判定并执行退款。每一步都更新售后单状态并通知双方。

举证

双方都必须留证

用户：商品问题图片/视频、服务未履约证明、聊天记录。商户：履约记录、核销记录、发货与签收凭证、服务过程记录。平台只依据系统内证据与双方上传材料判定。

判定结果

只有三种结论

全额退款、部分退款、驳回。判定必须选择责任方（商户 / 用户 / 双方 / 不可归责）并填写理由；结论对用户与商户同时可见。

资金执行

退款与扣款分离

退款从平台微信收款账户原路退回用户；同时冲减商户虚拟账户余额，商户应承担部分从待结算、可提现或后续结算中扣回，不足时形成负余额并限制提现。佣金按退款金额比例冲回。

不可逆操作 仲裁结论、手工退款、商户封禁、提现打款均为不可逆或高影响操作：必须二次确认、填写原因、校验权限，并写入不可删除的操作日志。财务打款与客服判定不能由同一人完成，避免既判又付。

7.2 佣金与结算（SR-02）

商品实付　　= Σ（商品售价 × 数量）− 商品级优惠（本期无优惠，等价于售价合计）
净商品实付　= 商品实付 − 退款商品金额
平台佣金　　= ROUND（净商品实付 × 佣金率，2）
商户可结算　= 净商品实付 − 平台佣金 + 配送费
  • 佣金率优先级：商户单独配置优先于类目默认值；未配置时使用类目默认值，两者都缺失则不允许上架。
  • 规则快照：按订单支付时间生成佣金率与结算规则快照；规则变更不追溯已支付订单，结算规则变更从下一账单周期生效。
  • 取整：佣金四舍五入到分，尾差计入平台佣金收入；商户可结算金额不做二次取整。
  • 配送费：P0 配送费由商户设置并全额归商户，不计入佣金基数；平台配送与补贴放到 P1。
  • 虚拟入账：每一笔订单在系统内生成收入、佣金、退款三条流水；结算只是把“待结算”转入商户虚拟收入账户的“可提现”余额，不发生实际资金划转。
  • 结算窗口：订单完成（签收 / 提货 / 核销）后 N 天进入可结算，N 由平台配置（建议默认 7 天 TBD）；售后中的订单金额冻结，不计入可提现。
  • 提现：商户发起提现需平台审核，财务线下银行转账并回填打款凭证；起提金额、提现手续费、打款时效 TBD，由财务确认后写入规则配置。
  • 提现状态：申请中 → 审核通过 → 线下打款 → 已打款；驳回则退回可提现余额并展示原因，已打款不可撤回。
  • 不做平台补贴抵扣：本期无平台补贴与优惠券，P1 引入时需明确补贴由平台承担，不得从商户结算中扣除。

试算只验证公式，实际佣金率以商户或类目配置为准。

资金冲回顺序

先扣待结算，再扣可提现

① 订单尚未结算：直接从待结算金额扣减。② 已结算未提现：扣减虚拟账户可提现余额。③ 已提现或余额不足：形成负余额挂账，从后续结算抵扣，并限制新的提现申请直到补足。

退款边界

只走原路，不做线下补偿

所有退款通过原支付渠道退回，到账时效以支付渠道为准（建议展示 1–3 个工作日 TBD）。平台线下打款只用于商户提现，不得用于退款或私下补偿；部分退款后订单保持已完成，并记录退款金额与原因。

7.4 核销与预约（SR-04）

核销

一单一码，商户执行

P0 一个订单一个核销码，多商品整单核销；部分核销放 P1。核销码动态刷新（建议 60 秒 TBD），截图不可用。商户扫码或输码，二次确认后提交，记录核销人与时间。

校验

四项校验缺一不可

① 订单属于本门店；② 订单状态为待履约；③ 在核销有效期内；④ 预约订单在预约时段允许范围内（建议前后 30 分钟 TBD）。任一不满足则拒绝并展示具体原因。

有效期

购买后生效，不随预约延后

服务券有效期从支付成功起算，默认 30 天，商品可配置 1–365 天 TBD。预约时段必须在有效期内；过期未核销按 SR-03 处理，是否退款以商品规则为准。

预约

时段容量与确认时限

商户按周配置时段模板与每时段容量，可临时关闭或加位。用户可预约未来 7 天 TBD；商户需在开始前 4 小时确认，超时未确认自动取消退款；用户可在开始前 2 小时免费取消 TBD。

爽约

记录但不自动扣款

预约时段结束仍未核销记为爽约，订单关闭。是否退款、是否限制再次预约由规则配置 TBD；P0 仅记录，不做惩罚性扣款。

商户闭店

主动通知与批量处理

商户临时闭店或平台封禁导致无法履约时，系统按未履约订单批量取消并退款，已预约订单通知用户改约或退款，不允许商户单方面失联。
