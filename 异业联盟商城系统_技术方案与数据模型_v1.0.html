文档与设计原则

这份文档回答三个问题：系统怎么分层、数据怎么建模、钱怎么记。P0 的目标不是搭一个“大而全”的架构，而是用最少的组件把一笔本地服务订单从支付、履约、核销、售后退款到结算提现完整跑通，并保证每一步可追溯、可对账。

设计原则

P1模块化单体优先

按领域划分模块与表归属，模块内高内聚；P0 不引入服务间网络调用与分布式事务。

P2交易强一致，通知最终一致

订单、支付、退款、记账在同一数据库事务内完成；通知、统计、内容分发走异步。

P3金额只用整数分

数据库统一 BIGINT 分，接口统一整数分，展示层格式化；佣金四舍五入到分并记录尾差。

P4状态机驱动

禁止直接 UPDATE 状态字段；每次迁移必须携带 from-status 条件与业务事件。

P5幂等与可重试

支付回调、退款、结算、提现、创建订单全部支持幂等键；失败可安全重试。

P6全链路可追溯

资金、状态、审核、规则变更均留流水与操作日志；不允许物理删除业务记录。

与 PRD 的对应关系 产品侧的“平台收款 + 商户虚拟收入账户 + 财务线下打款 + 订单完成 N 天后结算”在技术上落地为：平台现金账户 + 商户四类余额账户 + 复式记账流水 + 结算批次 + 提现单与打款凭证。业务状态与资金状态分开建模，避免“订单完成了但钱没记上”的中间态。
01

目标与约束

技术方案必须服从已经确认的业务边界；以下约束直接决定模型复杂度，开发中不得擅自放宽。

约束对技术方案的影响
单店单订单一笔支付只对应一个商户，不需要跨商户拆单与合并支付；分账模型可退化为“单商户虚拟账户”。
平台微信收款平台使用微信支付商户号收款；商户号、APIv3 密钥与证书由平台 PC 后台配置（T2 已确认），代码只读配置、不硬编码。系统不调起服务商分账，只做内部记账；退款从平台账户原路退回。
商户虚拟收入账户每个商户一个账户，至少包含待结算、冻结、可提现、提现中四类余额；账户余额与流水必须可对账。
财务线下打款P0 采用人工网银转账 + 回单上传（T7 已确认），不接银行代付/批量转账；系统生成提现单、财务审核、回填回单号与凭证 URL 后记账。
结算周期 N 天N 默认 7 天，平台 PC 后台可按商户配置（T8 已确认）；订单完成后生成结算项，due_at = completed_at + N 天，到期进入结算批次。
小程序 + H5同一套消费者 API；登录与支付方式按端区分；账户按 unionid 合并。H5 域名、ICP 与微信内 H5 支付均已具备（T4 已确认）。
商户中心复用小程序同一个微信小程序；商户中心是「个人中心」内的一个菜单，按角色路由进入；商户身份与消费者身份分离鉴权（T5 已确认）。
P0 无优惠券 / 会员 / 跨店P0 不支持跨店购物车、连锁多门店、会员积分与优惠分摊（T10 已确认）；扩展时新增订单组 / 商户层级，不修改 P0 核心表语义。

WHY MONOLITH

P0 不拆微服务

订单、支付、退款、记账需要同一事务边界；拆成服务会引入分布式事务、补偿与链路追踪成本。先以模块化单体交付，等结算/通知/统计出现独立扩容需求再拆。

关键边界 模块之间不允许直接修改对方的表：交易模块只能调用资金模块的记账接口，资金模块只能消费支付/退款/结算事件。报表可以跨表只读查询，但写操作必须回到模块归属。

04

核心流程与状态机

状态机的价值不是“画得好看”，而是让每一次状态变更都有明确的事件、守卫条件与副作用。下面先描述五条主流程，再用表格把状态迁移固定下来。

4.1 下单与支付

  1. 1
    提交结算客户端提交 merchantId、商品行、履约方式、地址或预约时段、幂等键。服务端不信任客户端传入的金额。
  2. 2
    校验与快照校验门店营业、商品上架、库存/时段容量、配送范围；生成商品价格、配送费、佣金率快照。佣金率解析顺序：商户覆盖值 → 类目默认值，解析结果快照到订单，结算不再重算。
  3. 3
    预占资源实物扣减可售库存并增加锁定库存；服务时段增加 reserved_count；失败则返回明确原因。
  4. 4
    创建订单写入 order（PENDING_PAYMENT，expire_at = now + 15 分钟）、order_item、order_status_log；金额全部为整数分。
  5. 5
    创建支付单调用微信支付统一下单，写入 payment_order（CREATED）；返回 prepay_id 给客户端。
  6. 6
    支付回调验签、校验金额、按 payment_no 幂等更新为 PAID；订单 PENDING_PAYMENT → PENDING_ACCEPT；发 OrderPaid。
  7. 7
    履约准备核销类生成 verify_code，预约类生成 appointment；商户收到新订单通知；超时任务开始计时。
  8. 8
    失败与超时15 分钟未支付关闭订单并释放库存/时段；支付失败保留待支付；重复支付识别后原路退回多余款项。
IDEMPOTENCY

创建订单与支付回调

创建订单使用 Idempotency-Key 唯一索引；支付回调以 transaction_id 唯一约束 + UPDATE ... WHERE status IN ('CREATED','PAYING') 双重保护，回调重复不会重复记账。

AMOUNT CHECK

金额以支付单为准

回调金额必须等于 payment_order.amount；若不一致，支付单标记异常，订单不进入待接单，转人工处理并告警。不允许“少付也发货”。

4.2 履约与核销

履约方式商户动作用户动作完成条件关键技术点
实物配送接单 → 填物流 → 发货确认收货确认收货或发货后 7 天自动确认物流单号仅记录，不做轨迹对接；自动确认由调度任务执行。
到店自提接单 → 备货完成 → 核销提货码到店出示提货码提货码核销成功提货码与核销码共用 verify_code 表，type 区分 PICKUP / SERVICE。
到店服务接单 → 确认预约 → 扫码核销选择时段 → 到店出示核销码核销成功核销前校验门店、状态、有效期、预约窗口；核销后不可撤销。
核销事务 核销必须在同一事务中完成：① 校验 verify_code 属于本门店且状态 ACTIVE；② 条件更新为 USED（WHERE status='ACTIVE'）；③ 订单 → COMPLETED；④ 写状态日志；⑤ 发 OrderCompleted（资金模块据此生成结算项）。任何一步失败整体回滚，禁止“码已用、订单没完成”。

4.3 售后与仲裁

  1. 1
    申请售后按订单类型与状态校验是否可申请；写入 after_sale，上传凭证；若尚未结算，冻结对应结算项。
  2. 2
    商户处理同意退款或拒绝（必填原因）；48 小时内未处理，调度任务自动转平台仲裁。
  3. 3
    平台举证客服受理，双方补充凭证；仲裁单记录责任方、判定金额与理由。
  4. 4
    执行退款调用退款接口，退款单 PROCESSING → SUCCESS；发 RefundSucceeded；资金模块冲回虚拟账户。
  5. 5
    结案订单/售后状态更新；通知双方；结算项解除冻结或标记调整；操作日志留存。

退款金额不得超过订单已支付金额减已退款金额；部分退款按订单行金额与佣金比例计算，尾差计入平台。

4.4 结算与提现

  • 1
    订单完成发 OrderCompleted；资金模块创建 settlement_item，状态 PENDING，due_at = completed_at + N 天（N 默认 7 天，按商户配置）。
  • 2
    每日批次调度任务选取 due_at 已到、未冻结、未结算的结算项，按商户生成 settlement_batch，状态 PENDING。
  • 3
    财务复核财务核对订单、退款、佣金；发布批次（PUBLISHED），执行记账：待结算 → 可提现 + 平台佣金收入。
  • 4
    商户提现商户申请提现，金额从可提现转入提现中；财务审核后人工网银转账，回填银行回单号与凭证，状态 PAID（T7 已确认）。

    • 订单主状态流

    待支付→ 待接单→ 待履约→ 履约中→ 已完成→ 售后中→ 退款中 / 已退款

    待支付、待接单均可取消并原路退款；服务订单核销即完成，不进入“履约中”。

    REFUNDINGREFUND_SUCCESSREFUNDED / COMPLETED渠道退款成功全额退款 → REFUNDED；部分退款 → COMPLETED 并记录退款金额

    其他关键状态机

    实体状态关键迁移与约束
    支付单CREATED → PAYING → PAID；PAID → REFUNDING → PARTIAL_REFUNDED / REFUNDED；CREATED → CLOSEDtransaction_id 唯一；金额不一致进入异常；退款累计不得超过支付金额。
    退款单REQUESTED → PROCESSING → SUCCESS / FAILED以 refund_no 幂等；失败可重试；成功后必须触发资金冲回。
    售后单APPLIED → MERCHANT_PROCESSING → MERCHANT_AGREED / REJECTED → ARBITRATING → RESOLVED → REFUNDING → COMPLETED / CANCELLED商户超时自动转仲裁；平台结论为最终；已退款不可再次申请同金额。
    结算项PENDING → FROZEN → PENDING / SETTLED；PENDING → SETTLED；PENDING → CANCELLEDorder_id 唯一；due_at 到期才可入批次；售后中冻结；全额退款且未结算可取消。
    提现单REQUESTED → APPROVED → PAYING → PAID；REQUESTED → REJECTED；PAYING → FAILED金额不得超过可提现；申请时从可提现转入提现中；驳回/失败必须退回。
    预约PENDING_CONFIRM → CONFIRMED → COMPLETED；PENDING_CONFIRM → CANCELLED；CONFIRMED → NO_SHOW时段容量条件更新；商户确认时限；取消时限；爽约记录但 P0 不自动扣款。
    核销码ACTIVE → USED / EXPIRED / INVALID一单一码；动态码由客户端展示但服务端以 code + 状态为准；核销不可撤销。
    商户PENDING → ACTIVE → RESTING / BANNED；ACTIVE ↔ RESTING；BANNED → ACTIVE停业/封禁停止新订单；在途订单按规则批量取消退款；已履约订单继续售后。
    商品DRAFT → PENDING_AUDIT → ON_SALE / REJECTED；ON_SALE ↔ OFF_SALE价格、主图、类目变更需重新审核；库存与描述微调可不重审。
    05

    数据模型

    数据模型围绕“订单是交易主线、虚拟账户是资金主线、结算项是两条主线的连接点”来组织。所有金额用整数分，所有业务记录保留状态与审计字段，不做物理删除。

    5.1 建模约定

    约定说明
    主键业务表统一 BIGINT 主键（雪花 ID 或数据库序列）；对外单号单独生成，如 LM202611070001、WX...、RF...。
    金额BIGINT，单位“分”；接口与库内一致；费率用 DECIMAL(5,4)（如 0.0500 表示 5%）。
    时间库内存 UTC；接口返回 ISO 8601；页面按 Asia/Shanghai 展示。
    状态枚举字符串（如 PENDING_PAYMENT），不使用魔法数字；状态变更写 order_status_log。
    删除业务记录只改状态，不物理删除；审计与资金流水永久保留。
    审计字段created_at、updated_at 必有；资金与治理表增加 created_by / updated_by / reason。
    快照订单保存商品、价格、佣金率快照；商户保存结算账户快照；规则变更不影响已支付订单。
    敏感字段字段级加密（AES-256-GCM）：收货人、联系电话、详细地址、银行卡、支付密钥与证书；密文列不可等值查询，登录手机号需另建盲索引（方案 TBD）。

    category 类目 product 商品/服务 product_sku 规格/库存 service_slot 预约时段

    06

    资金记账设计

    资金模块只做两件事：把业务事件翻译成借贷分录，并维护账户余额快照。任何绕过流水直接改余额的代码都不允许进入主干。

    6.1 账户体系

    账户性质含义
    PLATFORM_CASH资产平台微信收款账户中的资金；用户支付增加，退款/打款减少。
    MERCHANT_PENDING负债平台应付商户、尚未结算的金额；支付成功增加，结算/退款减少。
    MERCHANT_FROZEN负债售后或争议中冻结的金额；从待结算或可提现转入。
    MERCHANT_AVAILABLE负债商户可提现余额；结算入账增加，提现/退款减少，可为负。
    MERCHANT_WITHDRAWING负债已申请提现、等待线下打款的金额。
    PLATFORM_COMMISSION_REVENUE收入平台佣金收入；结算时确认，退款时按比例冲回。

    若订单已结算，则冻结从 MERCHANT_AVAILABLE 转入 FROZEN；解冻反向。冻结不改变平台现金。

    6.3 记账不变量

    • 借贷必平：每个 ledger_transaction 的借方合计必须等于贷方合计；日终对账任务再次校验。
    • 事务绑定：业务状态变更与记账事务在同一个数据库事务内提交；不允许先改状态后补流水。
    • 余额快照：merchant_account 余额在同一事务内按分录更新；ledger_entry.balance_after 记录快照，便于排查。
    • 幂等：同一个业务事件（支付成功、退款成功、结算发布、提现打款）只能产生一个记账事务；重复请求返回原结果。
    • 不可变：ledger_entry 只追加，不修改、不删除；纠错通过反向分录 + adjustment 记录。
    • 负余额：pending / frozen / withdrawing 不允许负数；available 允许负数，表示商户对平台的欠款，从后续结算抵扣。

    6.4 结算与提现时序

    阶段动作状态变化
    订单完成创建 settlement_item，计算 due_atorder: COMPLETED；item: PENDING
    售后申请未结算则冻结；已结算则冻结可提现item: FROZEN；账户 frozen ↑
    批次生成扫描 due_at 到期、非冻结项，按商户生成批次batch: PENDING；item 关联 batch_id
    财务发布核对后发布，执行结算分录batch: PUBLISHED；item: SETTLED；available ↑
    商户提现校验余额，冻结提现额withdrawal: REQUESTED；available → withdrawing
    财务打款线下转账，回填回单withdrawal: PAID；withdrawing → cash

    6.5 对账与异常

    RECONCILIATION

    四本账每天对一次

    ① 微信支付账单 vs payment_order；② 微信退款账单 vs refund_order；③ ledger_entry 汇总 vs merchant_account 快照；④ 提现单与银行回单金额。差异进入异常队列，由财务人工处理并生成 adjustment 分录。

    FAILURE

    失败不吞掉

    退款失败、打款失败、记账失败都必须保留原单据与失败原因；重试由调度器执行，超过次数转人工。禁止删除失败单据或直接改余额“抹平”。

    07

    接口设计

    接口按端分组，共用同一套领域服务。P0 只提供足够跑通主流程的接口，不为未来功能预留空接口；每个写接口都必须能回答“重复调用会怎样”。

    7.1 通用约定

    约定说明
    鉴权消费者与商户使用 Bearer Token；后台使用独立 Token + RBAC 权限点。商户 Token 必须携带 merchant_id，服务端再次校验数据归属。
    幂等创建订单、创建支付单、申请退款、申请提现、核销必须携带 Idempotency-Key；服务端以唯一索引落库。
    金额请求与响应中的金额统一为整数分，字段名以 _amount 结尾；禁止传字符串或小数。
    响应{ code, message, data, traceId }；业务失败用 code 区分，HTTP 状态码不承载全部语义。
    分页列表统一使用 page / pageSize（或游标），默认按创建时间倒序；返回 total 与 hasMore。
    时间ISO 8601，带时区；服务端统一 UTC 存储。
    追踪每个请求生成 traceId，写入日志并返回响应头；支付回调、退款回调同样记录 traceId。
    契约文件 P0 目标契约已落盘：contracts/p0-api.yaml，覆盖消费者、商户、平台与微信回调共 56 个操作；contracts/openapi.yaml 为已实现接口快照，由代码自动生成并在 CI 校验差异。

    7.5 回调与错误码

    CALLBACK

    微信支付回调

    POST /api/v1/callback/wechat/pay：验签 → 校验金额 → 幂等更新支付单 → 更新订单 → 记账 → 发事件 → 返回成功。处理失败返回非 200，微信会重试；本地必须能承受重复回调。

    CALLBACK

    微信退款回调

    POST /api/v1/callback/wechat/refund：按 refund_no 幂等；成功后更新退款单、订单/售后、资金冲回；失败记录原因并告警，不能吞掉。

    错误码含义处理建议
    ORDER_EXPIRED订单已超时关闭引导用户重新下单
    STOCK_NOT_ENOUGH库存不足提示剩余数量或推荐替代
    SLOT_FULL预约时段已满推荐最近可用时段
    PAY_AMOUNT_MISMATCH回调金额与支付单不一致进入异常队列，人工处理
    IDEMPOTENCY_CONFLICT同一幂等键对应不同请求体拒绝并告警，防止误用
    VERIFY_CODE_INVALID核销码无效/过期/非本店返回具体原因，不允许强制核销
    AFTER_SALE_NOT_ALLOWED当前状态不支持售后展示可售后条件
    REFUND_AMOUNT_EXCEEDED退款超过可退金额返回剩余可退金额
    WITHDRAW_BALANCE_NOT_ENOUGH可提现余额不足展示可提现余额
    SETTLEMENT_NOT_DUE结算项未到 due_at不可提前结算
    08

    并发、一致性与幂等

    P0 的并发风险集中在五处：库存、预约时段、支付回调、退款额度、提现余额。策略是数据库条件更新 + 唯一约束 + 事务，不依赖 Redis 锁保证资金正确性。

    场景策略关键约束
    库存扣减下单只锁定库存，支付成功后转已售；取消/超时释放。条件更新：stock - locked_stock - sold_stock >= ?；失败不生成支付单。
    预约时段下单预占名额；取消/拒单释放。reserved_count < capacity 条件更新；唯一键 (product_id, slot_date, start_time)。
    支付回调按 transaction_id 唯一 + 状态条件更新。UPDATE payment_order SET status='PAID' WHERE status IN ('CREATED','PAYING')；影响行数 0 视为重复。
    重复下单Idempotency-Key 唯一索引。同一键返回原订单；请求体不一致返回 IDEMPOTENCY_CONFLICT。
    退款额度退款前锁订单行，累计退款不超过已支付。refunded_amount + ? <= paid_amount；退款单按 after_sale_id 唯一。
    结算唯一结算项 order_id 唯一，批次状态守卫。已结算项不可重复入批次；批次 PUBLISHED 后不可再改。
    提现余额锁账户行，条件扣减。available_balance >= ?；申请时同时写 withdrawing，事务内完成。
    记账幂等ledger_transaction.idempotency_key 唯一。失败重试复用同一 key；已存在则直接返回原事务。

    事务边界

    MUST IN TX

    同一事务内完成

    订单状态变更 + 支付单更新；支付成功 + 记账；退款成功 + 退款单 + 记账；结算发布 + 批次/结算项状态 + 记账；提现申请 + 余额转移；核销 + 订单完成 + 结算项生成。

    AFTER COMMIT

    提交后再异步

    订阅消息、站内信、统计更新、内容缓存刷新、对账导出。通过 Outbox 事件驱动，失败可重试，不影响主交易结果。

    Outbox 与调度任务

    任务频率/触发作用
    订单超时关闭每分钟扫描 expire_at关闭未支付订单，释放库存/时段，关闭支付单。
    接单/发货超时每分钟扫描商户超时未接单自动退款；发货超时提醒并进入平台介入。
    自动确认收货每小时扫描发货后 7 天未确认，自动完成订单。
    预约确认超时每分钟扫描商户未在开始前 4 小时确认，自动取消退款。
    售后超时转仲裁每小时扫描商户 48 小时未处理，转平台仲裁。
    结算批次生成每日一次扫描 due_at 到期、未冻结的结算项，生成批次。
    Outbox 投递每秒/每 5 秒发送通知事件；失败重试并记录次数。
    对账任务每日一次支付/退款/账务/提现四本账核对，输出差异队列。

    定时任务使用数据库租约锁或 Redis 锁选主，保证同一任务只在一个实例执行；任务本身必须幂等，重复执行不产生重复退款或重复结算。

    09

    安全、权限与审计

    三端身份必须严格分离：消费者 Token 不能调用商户接口，商户 Token 不能跨门店，后台 Token 不能绕过 RBAC。资金与审核动作必须二次确认并留痕。

    9.1 身份与鉴权

    端登录方式Token 内容边界
    消费者小程序wx.login → code2sessionuserId, unionId, role=CONSUMER仅本人订单/地址/售后
    消费者 H5微信内网页授权；非微信环境短信userId, unionId, role=CONSUMER与小程序共享账户
    商户中心小程序登录 + 商户身份绑定userId, merchantId, role=OWNER/CLERK仅本门店；店员不可见金额/提现
    平台后台账号密码（财务/超管建议二次验证）adminId, role, permissions按权限点与数据域

    9.2 权限与数据隔离

    RBAC

    最小必要权限

    超管、运营、审核员、客服/仲裁、财务、店长、店员。运营不碰钱、财务不碰商品、客服可判定但不能单独打款、店员不接触金额。权限点与 PRD SR-05 一致。

    DATA SCOPE

    商户数据按门店隔离

    所有商户接口强制校验 merchant_id 归属；后台查询商户数据必须记录访问日志。平台财务可跨店查资金，但不可修改商品与订单履约状态。

    9.3 敏感数据与接口安全

    • 脱敏展示：后台用户手机号、地址、银行卡号默认脱敏；只有必要角色可申请查看完整值，并记录查看日志。
    • 加密存储：手机号、地址、提现银行卡完整卡号、身份证号等敏感字段加密存储（T9 已确认）；日志与导出文件不得包含明文。数据留存期限仍待法务确认 [TBD]。
    • 回调验签：微信支付回调必须验证签名、时间戳与随机串，校验商户号与金额；拒绝重放。
    • 限流：登录、短信、下单、核销、提现申请按用户/IP/门店限流；异常频率触发风控标记。
    • 文件上传：限制类型与大小，私有读；图片 URL 使用临时签名；禁止上传可执行文件。
    • 密钥管理：微信支付商户号、APIv3 密钥与证书由平台 PC 后台配置并加密存储（T2 已确认），仅授权角色可管理；数据库密码、对象存储密钥放环境变量 / 配置中心；均不入代码库与前端包。
    • 审计：审核、规则、仲裁、退款、打款、商户状态、用户状态、权限变更全部写 operation_log，保留前后值。
    资金合规提示 系统只实现“平台收款 + 虚拟账户 + 线下打款”的记账，不解决二清合规本身。收款账户隔离、商户结算协议、打款凭证留存与税务口径必须由财务/法务在上线前确认（对应 PRD Q1）。

    10.1 指标与告警

    指标/告警触发条件处理动作
